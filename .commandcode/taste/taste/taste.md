# Taste
- Communicates in Chinese and expects answers in Chinese (asked "分析项目如何部署", "给出具体的部署步骤"; assistant correctly answered in Chinese). Confidence: 0.8
- When asking for system/architecture analysis, explicitly requests it be done without exposing concrete code ("不暴露具体代码"): prefers conceptual explanations — layered diagrams, data flow, responsibilities, security boundaries — over pasted source or config snippets. Confidence: 0.7
- Asks for an analysis/overview first, then drills in for concrete, actionable steps ("给出具体的部署步骤") rather than stopping at a conceptual summary. Likes progressive depth: high-level picture → exact commands/paths grouped by phase. Confidence: 0.6
- Expects deployment/ops answers to be grounded in the actual repo files and docs, with precise commands, file paths, and caveats — not generic or invented steps. Confidence: 0.6
- Asks for branch/PR work to be verified against the repo's own documented standards before merge (e.g. "查看当前分支的开发是否符合要求"): expects real tests to be run, conventions checked (tool-name references, Skill frontmatter, licensing/attribution), and a clear verdict that separates must-fix issues from suggestions. Confidence: 0.6
- Moves from "how do I do this?" to hands-on execution quickly ("开始进行部署"): wants the agent to actually run the deployment/ops steps end-to-end on their machine (env probe → venv → config → start → verify), not stop at giving instructions. Confidence: 0.5
- Wants implementation scope enumerated as a structured, trackable task table/list rather than prose ("将可以做成插件的列出任务表"): expects per-task fields such as ID, target layer, deliverable, dependencies, and acceptance criteria. Confidence: 0.5
- Prefers to reuse the project's existing extension mechanisms (Hermes plugins / MCP services / Skills / Open WebUI functions) to deliver new features, repeatedly asking whether requirements can be done as plugins (e.g. "都可以做成插件", "可视化不能做成插件吗") before considering new standalone services. Confidence: 0.6
- When a new component is to be built, expects it to be formally named and specified ("正式命名并列出详细计划"): concrete plugin/toolset names, version, tool signatures, repo file layout, algorithm/behavior rules, explicit non-goals, milestones, risks, and an acceptance checklist. Confidence: 0.6
- Pushes back on absolute or negative conclusions ("可视化不能做成插件吗") and expects the agent to re-verify against the source and revise its answer rather than defend the earlier claim. Confidence: 0.55
- Wants an explicit gap report separating implemented from not-yet-implemented functionality ("还未实现的功能"), including honest acknowledgement when requirements name a tech stack (e.g. Django / Vue.js / MySQL / LangChain) that does not exist in the repo — planned architecture must not be presented as delivered. Confidence: 0.55
- When implementation begins, expects the code to follow the project's own existing documentation and conventions ("按照插件开发文档进行开发") rather than inventing new patterns — new components should match the documented contracts and mirror existing sibling implementations. Confidence: 0.5
- Insists that new dependencies go into the project's own requirements (e.g. a component-scoped `requirements.txt`) and that the project virtual environment be used — never install packages into the local global Python interpreter ("不要在我本地的python全局环境中加东西"). Confidence: 0.75
- After a new component is built, re-verifies that it is actually wired into the end-to-end workflow ("检查这个前沿分析是否和整个研究流程有联动"): expects a component to be reachable/routed from the existing pipeline (e.g. an upstream Skill pointing to its tools, artifact hand-off to downstream writing steps), not just newly created in isolation. Wants any broken links named explicitly along with small, concrete fixes. Confidence: 0.6
- For "where should I change the code" questions, expects pinpoint, actionable locations — exact files, key line ranges/functions, and which existing parts can be reused — not just a conceptual description. Confidence: 0.5
